
Сбор данных в `targetmap` организован как последовательность независимых шагов. Каждый сборщик получает входные параметры, обращается к своему источнику и сохраняет исходный результат в JSON-снимок.

Сбор и интерпретация разделены: сборщик фиксирует ответ источника, а `normalize.py` определяет, какие сведения могут стать признаками оценки.

## 1. Общий формат снимка

Все сборщики используют общую функцию `save()` из `collect/_common.py`.

Результат сохраняется по пути:

```
data/raw/<object_key>/<YYYY-MM-DD>/<collector>.json
```

Каждый файл имеет единую внешнюю структуру:

```
{
  "collector": "dns",
  "object": "clinic-example",
  "collected_at": "2026-10-31T12:30:00",
  "observed_at": "2026-10-31",
  "log": [
    {
      "level": "ok",
      "message": "A: 2 записей"
    }
  ],
  "log_summary": {
    "ok": 1
  },
  "data": {}
}
```

Основное содержимое находится в `data`. Его внутренняя структура зависит от сборщика.

- `collector` - имя сборщика.
    
- `object` - ключ оцениваемой организации.
    
- `collected_at` - фактическое время сохранения результата.
    
- `observed_at` - дата снимка.
    
- `log` - последовательность сообщений о выполненных шагах.
    
- `log_summary` - количество сообщений каждого уровня.
    
- `data` - результат сбора.
    

Снимок сохраняется и при отказе источника. В таком случае `data` содержит доступную диагностику, а журнал фиксирует причину. Это позволяет отличить отсутствие признака от отсутствия проверки.

## 2. Последовательность сбора

Основной сценарий запускается через `run_object.py`. Порядок шагов учитывает зависимости между источниками.

```
crt.sh
  │
  ▼
DNS ────────────────────┐
  │                     │
  ├──► Censys           │
  │                     │
  ▼                     │
dnstwist                │
  │                     │
  ▼                     │
fingerprint             │
  │                     │
  ▼                     │
zakupki                 │
                        │
                        ▼
                 JSON-снимки
                        │
                        ▼
                  normalize.py
                        │
                        ▼
                   full_run.py
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
         db_load.py           exports_build.py
             │                     │
             ▼                     ▼
       observations.db       карточки и отчёты
```

Схема показывает логические зависимости, а не то, что каждый сборщик передаёт данные следующему напрямую. Между шагами используются сохранённые снимки.

### Шаг 1. `crt.sh` - поиск доменных имён

**Вход:** основной домен организации.

**Источник:** журналы прозрачности сертификатов `crt.sh`.

**Выход в** `**data**`**:**

- `hosts` - найденные доменные имена;
    
- `wildcards` - подстановочные имена;
    
- `flagged` - имена, похожие на служебные;
    
- `first_seen` - дата первого появления имени;
    
- `issuers` - сведения об издателях сертификатов.
    

Имена сами по себе не считаются признаком существующего узла. Они передаются на следующий этап для проверки DNS-разрешимости.

### Шаг 2. `dns_collect` - проверка DNS и почтового канала

**Вход:**

- основной домен;
    
- список имён `hosts` из снимка `crt.sh`, если он доступен за ту же дату.
    

Если снимок `crt.sh` отсутствует, проверяется только основной домен.

**Источник:** два публичных DNS-разрешителя - `8.8.8.8` и `1.1.1.1`.

**Выход в** `**data**`**:**

- `a`, `mx`, `ns`, `txt` - записи DNS;
    
- `*_quality` - качество ответа для каждого типа записи;
    
- `spf` - наличие записи и её политика;
    
- `dmarc` - наличие записи и её состояние;
    
- `hosts_checked` - результаты проверки имён из `crt.sh`;
    
- `addresses` - соответствие IP-адресов доменным именам.
    

Ответы двух разрешителей сопоставляются. Если ответил только один или результаты расходятся, это отражается в качестве наблюдения.

**Передача дальше:** подтверждённые адреса из `a` и `addresses` используются сборщиком Censys.

Имена, указывающие на один IP, объединяются в один узел. Это предотвращает многократный учёт одного адреса.

### Шаг 3. `dnstwist` - поиск доменов-двойников

**Вход:** основной домен.

**Источник:** инструмент `dnstwist`.

**Выход в** `**data**`**:**

- `forks` - зарегистрированные варианты домена;
    
- `fuzzer` - способ генерации варианта;
    
- `a`, `mx`, `ns` - DNS-записи варианта;
    
- `idna` - представление домена в punycode, если требуется;
    
- `mail_ready` - наличие почтового сервера;
    
- дополнительные показатели регистрации и обезвреживания вариантов.
    

Сборщик не открывает сайты найденных доменов и не получает их баннеры или скриншоты.

Результат сохраняется отдельно и используется при формировании аналитического лога. В текущем `full_run.py` данные `dnstwist` напрямую не участвуют в числовом расчёте индекса.

### Шаг 4. `fingerprint` - анализ главной страницы

**Вход:** основной домен.

**Источник:** главная страница организации.

Выполняется запрос главной страницы, без обхода внутренних разделов.

**Выход в** `**data**`**:**

- `headers` - отдельные HTTP-заголовки;
    
- `markup` - обнаруженные признаки платформ;
    
- `external_hosts` - внешние домены из разметки;
    
- `vendors` - распознанные поставщики и признаки именования поддоменов по объекту.
    

**Передача дальше:** список доменов поставщиков используется в `normalize.py` при атрибуции IP-адресов и оценке зависимостей от третьих сторон.

Само упоминание домена поставщика не означает подтверждённого доступа к системам организации.

### Шаг 5. `zakupki` - государственные контракты

**Вход:** ключ объекта, ИНН и список контрактов.

**Источник:** Единая информационная система закупок.

Сборщик поддерживает передачу списка контрактов в JSON. Автоматический поиск через форму сайта в текущей реализации не выполняется.

**Выход в** `**data**`**:**

- `inn` - ИНН организации;
    
- `contracts` - переданный список контрактов;
    
- `state_contracts_sum` - сумма контрактов;
    
- `entry_method` - способ внесения;
    
- `status` - результат проверки.
    

Результат сохраняется в отдельном снимке. В просмотренной версии `full_run.py` данные закупок напрямую в расчёт индекса не включены.

### Шаг 6. `censys` - сведения о службах

**Вход:** IP-адреса из DNS-снимка того же объекта.

Адреса берутся из записей `a` и из соответствия `addresses`. Запрос выполняется к Censys Platform API по каждому адресу отдельно.

**Источник:** база внешней инфраструктуры Censys. Обращений к самим узлам организации не выполняется.

**Выход в** `**data**`**:**

- `addresses` - список запрошенных адресов;
    
- `states` - состояние запроса по каждому адресу;
    
- `hosts` - ответы API по адресам;
    
- `note` и `limitation` - пояснения о способе сбора и ограничениях.
    

Токен передаётся через переменную окружения `CENSYS_TOKEN` и не записывается в снимок.

Censys запускается последним, потому что ему нужны адреса, подтверждённые на этапе DNS. Отказ API или отсутствие записи у оператора не трактуется как отсутствие службы на самом узле.

## 3. Переход от снимков к наблюдениям

После сбора исходные JSON-файлы читает `normalize.py`. Он не выполняет сетевых запросов, а интерпретирует сохранённые результаты.

Основные переходы:

|Исходные данные|Обработка|Результат|
|---|---|---|
|DNS + Censys|Атрибуция IP и проверка служб|Собственные, сторонние, исключённые и непроверенные узлы|
|DNS TXT|Проверка политик SPF и DMARC|Признаки почтового канала|
|Fingerprint + DNS/Censys|Сопоставление доменов и принадлежности адресов|Наблюдения о зависимостях от третьих сторон|
|Censys services|Проверка типов служб и портов|Основания для покрытия техник ATT&CK|
|DNS + fingerprint|Проверка условий применимости|Дополнительные основания для оценки достижимости|

Для группы достижимости `normalize.py` формирует структуру периметра с отдельными списками:

- `own` - собственные узлы с наблюдаемыми службами;
    
- `supplier` - адреса, отнесённые к инфраструктуре поставщика;
    
- `unchecked` - узлы, принадлежность или службы которых не удалось установить;
    
- `excluded` - адреса, исключённые по результатам атрибуции;
    
- `mail` - нормализованные наблюдения почтового канала.
    

Для третьей стороны формируется отдельный результат с полями `value`, `status`, `credibility`, `sources` и пояснением. Он передаётся в расчёт вместе с данными периметра.

## 4. Расчёт и сохранение результатов

`full_run.py` объединяет нормализованные наблюдения с дополнительными входными данными:

- `objects.json` - перечень оцениваемых организаций;
    
- `reference.json` - референсные распределения;
    
- `manual.json` - данные, внесённые аналитиком;
    
- выгрузки реестров ОМС;
    
- снимок уровня сегмента `attack.json`.
    

Для каждого объекта формируются признаки интереса, достижимости и применимости поверхности к типам нарушителей. Затем рассчитываются индекс, полнота наблюдений и уровень оснований.

После расчёта:

1. `db_load.py` записывает объекты и наблюдения в SQLite.
    
2. `exports_build.py` формирует сводную таблицу, лог ненайденного и карточки организаций.
    
3. `trace.py` позволяет разобрать расчёт выбранного объекта и сверить результат с основным конвейером.
    

Полная последовательность обработки сохранённых данных запускается через `run_all.sh`. Этот сценарий не выполняет сетевой сбор: он использует уже созданные снимки.

## 5. Важные границы текущего workflow

- `crt.sh` предоставляет кандидатов для DNS-проверки, но не подтверждает существование узла.
    
- Censys получает адреса из DNS и читает сведения из собственной базы, не обращаясь к инфраструктуре объекта.
    
- `dnstwist` и `zakupki` сохраняют результаты сбора, но в текущей реализации напрямую не участвуют в числовом расчёте `full_run.py`.
    
- ОМС и референсные данные поступают в расчёт из отдельных файлов и выгрузок, а не из сетевых сборщиков.
    
- Даты снимков могут различаться: каждый источник выбирается по собственной последней успешной дате. Поэтому итоговая карточка показывает даты наблюдений отдельно.
    

Такое разделение позволяет проверить каждый этап независимо: исходный ответ источника, его нормализацию и использование в расчёте.
